**§26 的三条结论**（铺路策略）：
1. **蔓延的根在「路径漂移」，不在价格或额度**：`planRoadPath` 选终点时"边遍历边更新 best"会漏格
   （理论最优格 (15,8) 被跳过、给出 (22,4)），路径每 10 秒换一次方向 → 路铺成一片。
   改成**确定性地选终点**（遍历全部可达格取 h 最小、平局取字典序）后，AI 从铺满 100 格变成 **22 格**
   —— 连完半区内资源点就自动停下。**"路太多"往往不是"太便宜"，而是"没有终点概念"。**
2. **用价格抑制铺路，在本作里无效**：三档递增（每 20 / 10 / 5 格 +1⚡）实测，**铺路格数一模一样**
   （玩家 100 顶满额度 / AI 35~43）—— 铺路是被「额度上限 + 想铺就铺」驱动的，不是被钱劝退的。
   涨价唯一的效果是总花费翻倍（200 → 480~650⚡）并挤占建造/训练（训练士兵 106→64、胜率 90%→73%）。
   **`roadPriceStep` 已默认关闭（0），机制保留。**
3. **限制型 / 加价型规则必须先用跑批证伪**：§25 的额度三档、§26 的价格三档，两次都是"想当然会有效"、
   实测才发现要么掐死主循环、要么毫无作用。**跑批是这类改动的唯一裁判。**

**§25 的三条结论**：
1. **"功能写完了没接线"是本项目的重复病**：AI 政策（`aiPickPolicy` 全写好、就是没人发 offer）、
   `Engine.save`（存档模块写好了、0 处调用）、`Sandbox.addMove`（定义了没人调）。
   **改一个功能前先搜一遍它是不是已经有了、只是没接上。**
2. **额度不能卡死扩张**：roadCap 90 时终局主城 P50 掉回 2、星级归零（铺不够路 → 抢不到资源点 → 升级慢）。
   实测 90/100/120 三档后定 **100**。**任何"限制型"规则都要用跑批验证它没把主循环掐死。**
3. **单靠额度压不住蔓延**：道路总数 无上限 220 / 90 时 182 / 100 时 202 / 120 时 229 ——
   说明真正的观感问题在**铺路策略（贪婪铺块 vs 修主干）**，不是价格或额度。要彻底解决得改 AI 与
   推荐玩家的铺路方式，不是继续加价。

**§24 的四条结论**：
1. **"内容做完了但活不到"是数值问题，不是内容问题**：主城升满要 515⚡，而一局能量净收入只有 ~720⚡，
   还要付道路(~160)+卡牌(~90) —— **数学上就不可能**。改成本 515→240 后，Lv4/Lv5、黄金政策、
   士兵上限 120~140 立刻变成可达内容（终局主城 P50 2→4，Lv5 首次达成 881s）。
2. **门槛定在"实测 P50"等于必然失败**：每星要求 5 项**全部**达成，5 项各自都在 P50 附近 →
   联合概率趋近于零（实测 30/30 局 0 星）。门槛要按分位设计：★1≈P10~P25 / ★2≈P50 / ★3≈P75~P90。
3. **真人模拟测试的收益极高**：写 `test/_humanplay.js`（只用真实鼠标事件、不预设剧本）后，
   一局就抓出两个固定剧本永远碰不到的 bug ——
   ① 买不起**道路/效果牌**时商店抛异常（写死 `CFG.buildings[type]`）② 点**物流点**抛异常（`RES_META` 漏登记）。
   两个都表现为"点了没反应"，且**都发生在点击处理器里**（踩坑 #1 的形态）。
4. **测试自身的 bug 最隐蔽**：`selftest` 里那条"主城升满需 515 能量"的用例，
   拿 `rich()` 之后的余额当"一局收入"，算出十万级天文数字 —— 断言永远成立，等于没测。
   **改成断言设计不变量（升满成本 < 一局收入）才有意义。**

**§23 的四条结论**：
1. **项目此前没有 git**（`git rev-parse` → `not a git repository`）。对一个用来找工作的作品集项目来说，这不是洁癖问题：
   "我一个人从零做到现在"无法自证。已建仓（含 `.gitignore` 取舍，见 §23.1）。
2. **测试用的 `ff()` 会掩盖 bug**：`ff()` 末尾显式调了一次 `UI.render()`，
   于是"对局结束后结算卡不出现"这个真 bug 在测试里永远看不见（§23.2）。**这类"测试辅助函数替被测代码做了事"的坑要警惕。**
3. **表现层要"看得见"才是表现层**：第一版落成动画用 easeOut，30ms 内就冲到满高，
   压扁那一瞬根本看不见 —— 靠**放大截图**才发现，改成 easeIn 才对（§23.3）。
4. **game.js 保持纯逻辑**：特效走 `Game.fx` 事件队列（只放数据、不入 state、限长），
   渲染层消费并负责震屏/音效。这样分层没破，无头测试也不受影响。

**§22 的三条结论**：
1. **"文字可读"和"美术透出"不用二选一**——不要全局降蒙版，而是**只把文字那一块局部压暗**
   （`.menu-inner` 上一层 radial 柔光暗斑），美术区保持接近原图亮度。用户否掉的正是"全局压暗"这个思路。
2. **底图必须先裁成标准 16:9 再进工程**（1536×864）。原来靠 `background-size: cover` 现场裁，
   切多少是"算"出来的、不确定；预裁后裁切量确定，**且能顺手把右下角水印吃掉**。
3. **i2i（图生图）挪画面元素是有代价的**：为了"把城堡挪开按钮"，用 i2i 重绘了一版，
   功能成功但**整幅画风格漂移（变淡、笔触变弱）**。美术资产能用就别用 i2i 大改——用户最终选了原图。

**⚠️ 老问题处置结论**（2026-10-10 全部结案，见 §29.1）：
- **铺路蔓延 → 结案**：AI 侧主干式根治（§26，100 → 34 格）；玩家侧**不做额外约束** —— 用户设计判断：「真人玩家不会肆意铺路，铺路一定有目的性（路的尽头有资源点 / 能派兵抢占城池）」。脚本玩家铺满 100 格是脚本策略缺陷，不代表真人；额度 100 保留作硬兜底。
- 粮食过剩 → §25 已缓和；§26.6 的回升源于脚本玩家少出兵（用户拍板暂不处理）。
- 主城 Lv4/Lv5 死内容 + 任务→遗物链断 → §24 已治（AI 任务线亦已补齐，§29）。

## 1. 一句话定位与核心闭环

**定位**：以抽卡建城为核心、经营构筑为过程、战争验证构筑的 1v1 轻策略卡牌游戏（策划求职作品集）。

**核心闭环**：抽卡 → 建城 → 生产 → 出兵 → 抢资源点 / 占敌方建筑 → 获得新生产能力 → 再经营 → 攻主城。

**一句话规则总纲（V0.4）**：
> 二资源（⚡能量驱动卡牌与升本、🌾粮食驱动军事）；一切建筑由卡牌而来；**道路是城市的骨架与战争的血管**（建筑沿路生长、军队沿路行军、抢资源点先修路）；战争为数量抵消 + 等量交换攻城，防御值归零即占领；**摧毁敌方主城获胜**；**1800s 兜底**——到时仍未分胜负则按综合分判（`CFG.time.limit`）；AI 与玩家同一套规则。

**时间模型**：全局即时制 + 10 秒经济 Tick + 实时自动战斗；**正计时**，顶栏常驻 `Tick N / 180　剩 MM:SS`（§20 起，让兜底时限可见）。

### 地图

## 6. 踩过的坑与经验（隐性知识，最有价值）

1. **交互层的 TypeError 不会白屏**——它只杀死当前事件处理器，表现为"点了没反应"，console 有红色报错但用户不看。静态方法完整性检查是这类 bug 的廉价疫苗
2. **删一个函数时，它的副作用要跟着迁移**——曾删掉 `Game.pickRewardCard` 时丢了 `pendingReward = false`，导致弹窗重开死循环
3. **"点击后界面刷新了但状态没变"** → 优先查触发条件的**重入循环**
4. **新增卡牌种类时，`endDrag` 的分支链是"每种卡一份行为清单"**：拖地图/拖弃牌区/点击使用/取消，漏一条就是静默失效（道路牌曾漏掉弃牌区）
5. **进入"放置/瞄准模式"时不要移动资源**——模式只是"下一个点击的意图"，资源在动作成功时才消耗（道路牌多格预扣是特例）
6. **CSS 多轮叠改后应追加"最终覆盖块"**，而不是继续在中间打补丁
7. **裁切类 bug 的根治**：把固定 `height` 换成 `min-height`，结构上不可能再裁
8. **Python 批量替换的计数器会骗人**（applied 0 但实际生效）→ **改完必须 grep 验证**
9. **测试自己也会写错**：循环上界用了会随循环变化的量、测试格子选到资源点（会先结算守军）——报错时先怀疑测试
10. **双方对称性**是本项目的高频 bug 源：任何新规则都要写一个 p1/p2 双向断言
11. **"打不穿"先查账本，再查数值**：本轮差点误诊为数值问题，实际是造兵 bug。**跑批出现异常数量（兵力 1105、升级 134 次）时，异常本身就是 bug 的指纹**

### 第四十次修订新增（2026-10-03，都是真金白银换的）

12. **验证阈值定太低 = 自己骗自己**。上一轮路面断言 `CORE_MIN=25`，于是"人眼根本看不见的 Δ16~21"判通过，
    还拿官道格的高 Δ（64~104）去充数，掩盖了非官道格的问题 → 用户报"路面淡到根本看不清"。
    **定阈值先想清楚"这个数值对应什么观感"**，不要拿"测试能跑通"当验收标准。现值 45/38/22。
13. **采样/断言的"方向"必须跟着被测对象的走向走**。我测"路肩是否还是草地"时，
    无差别地对四个方向 ±0.42 取 max，结果**转角格的"沿路方向"必然是路**，得出"路面铺满整格"的假结论，
    白白排查半天。相邻格的路面是从格心连到格心的，**沿路方向永远是路**，只有垂直方向才叫路肩。
14. **改"阵营判定"前先确认数据结构是共享的还是分边的**。我以为 `isCastleAt`（不限阵营）是 bug，
    改成只认己方主城 → **敌方 AI 铺路前沿直接归 0**，自检挂 3 项。
    实际上道路是**双方共用一套 `state.roads`**（设计上"最后一段走玩家自己的路，道路互通"），
    敌方起步就得挨着自己主城铺。真正的缺陷是"玩家点击没有前沿限制"，不是判定不限阵营。
15. **参数标定要先扫一轮再下结论，别顺着直觉走**。加深路面（加 alpha / 压暗路缘）是直觉方向，
    实测却让偏土色的底图**更糊**（Δ 不升反降）；真正有效的是**提亮路心**。
    `test/_calib_road.js` 就是为此写的：候选参数组扫一遍，两列指标一起看。
16. **"提示文案写了什么"必须和"代码实际做了什么"对齐**。提示写"按 Esc 或点击其他区域取消"，
    实际只有 Esc 有效 → 玩家困在模式里出不来，直接被报成"卡死"。
    **写提示时顺手确认那条路径真的实现了**。
12. **统计口径用错会得出完全相反的结论**：`totalTroops`（场上）/ `inAirTroops`（空中）/ `activeTroops`（场上+空中）三者不等价；"场上 + 全部 march.n"是双计，只算场上会让派出瞬间腾出名额
13. **诊断要输出"死在哪一格"**：只看到"主城 HP 没掉"无法定位。记录每波的出发兵数 / 路径长 / 终止格 / 剩余兵，一眼看出是没走到还是走到了啃不动
14. **改状态前问"这个对象还有别名吗"**：`march.n` 是格子兵的账面别名，改一边不改另一边就是凭空造兵或部队消失

### 21.1 地图「绿幕」= 相机露底（方案 2：底图边缘模糊镜像外扩）

**先说根因（实测确认，不是猜素材）**：
- 画布底层是 `COL.bg`（原 `#44692f` 草绿平涂）。
- `clampCam()` 在地图**比画布小**时**只居中、不放大**；`zoomAt()` 把缩放下限写死 **0.45**。
- 实测：scale 0.45 时地图 783×405 vs 画布 1266×459 → **左右各露 242px、上下各露 27px 纯绿**。
- 默认 scale=1 时地图 1740×900 比画布大 → **不露**，所以玩家是**滚轮缩小后**看到的。

**实现（`js/sandbox.js`）**：
- 新增 `buildPlateExt()`：offscreen canvas 合成「中心原图 + 四边四角镜像平铺」→ 整张 `blur(18px) brightness(0.86) saturate(0.92)` → 中心贴回清晰原图 → 四边加 130px 暗角柔化接缝。结果缓存为 `plateExt`（按 `im.src` 去重，一张底图只构建一次）。
- `drawTiles()`：判断 `地图宽/高 × scale < 画布` 时改画 `plateExt`（画在 `-PLATE_PAD` 处），否则照旧画原图。
- `COL.bg` → `#1b2417`（近黑暗橄榄），即便外扩不可用也不像穿帮。
- **无头兼容**：无 `document.createElement` / 无 2d context 时 `buildPlateExt()` 返回 false，自动退回平涂（`smoke.js` 的假 canvas 正是这条路，所以冒烟照过）。

### 23.2 ★ 修掉一个真 bug：对局结束后结算卡不出现

**根因**（读 `main.js` 的 `scene.update` 发现）：
```
Game.update(dt);
if (S.tickCount !== lastTick) { lastTick = S.tickCount; UI.render(); return; }   // 全量渲染只在这里
lightAcc += dt; if (lightAcc >= 0.12) UI.refresh();                              // 否则只做轻量刷新
```
对局一结束，`Game.update` 立刻 `return`（`S.over`），**`tickCount` 再也不变** →
主循环永远走 `refresh()` 分支 → 而**结算卡与结算演出只在全量 `render()` 里触发**
→ **破城后画面毫无反应**。真实场景：AI 打掉我方主城，玩家看到"游戏无声结束、没有结算画面"。

**为什么测试一直没发现**：`fulltest` 的辅助函数 `ff(n)` 实现是
`for (i<n) Game.update(1); UI.render();` —— **末尾那句中括号外的 `UI.render()` 替被测代码干了活**，
把 bug 完整地掩盖掉了。这是"测试辅助函数越权"的典型。

**修法**：`scene.update` 里补一次全量渲染，用现有状态做守卫、不会每帧重渲染：
```js
if (S.over && !UI._resultShown) { UI.render(); return; }
```
**回归测试**：新增 `fulltest` 步骤 **S13d**，故意**不调用 `UI.render()`** 触发破城，断言结算卡会自动出现（34 → **35 步**）。

## 26. 第四十七次修订（2026-10-10）：铺路策略改造 —— 主干式算法 + 经济约束实测

### 26.0 用户决策

| 4 | 实施方式 | **分两步走**，每步跑批；"多测试，有问题随时改" |

### 26.1 第一步：主干式铺路（治观感，也是真正省能量的那一步）

**改前**：`enemyRoad()` 在"铺路前沿带"里选离目标曼哈顿距离最近的格。前沿带会越铺越宽，
且目标被"最近的未占资源点"不断牵走 → 路呈放射状铺散（AI 铺满额度 100 格）。

**改后**（全部在 `js/game.js`）：
- 新增 **`pickRoadGoal(side, needBuildings)`**：选一个目标后**锁定**，走完整条路径才换。
  只挑"未占 + 还没通路 + 在本方半区"的资源点；己方建筑够多才转攻敌方主城。
- 新增 **`planRoadPath(side, goalCells)`**：Dijkstra（走己方可走格代价 **0** → 优先复用已有路、
  不重复铺；走可铺空格代价 **1**、官道 **0.5**，保留 §14.1 的官道偏好）。
  **终点确定性地选**：遍历全部可达格取 h 最小、平局取 key 字典序。
  到不了目标时**退化为"朝目标推进到能到的最远处"**，而不是返回空 ——
  否则 A\* 一旦失败就返回空，AI 再也不铺路，等于把手绑住。
- **`enemyRoad()`** 改为"目标锁定 → 只铺路径的下一格；路径走完/目标失效才重选"。
- 新增 `roadableTile()`，并把 `canPlaceRoad()` 重构为 `roadableTile() && roadAdjacentAny()`（等价）。
  路径规划**必须**用前者：`canPlaceRoad` 基于**当前**状态（相邻必须有路），
  规划时用它会一步都走不出去。
- ⚠️ **物流点的自动铺路刻意没改** —— 它是玩家侧的自动功能，用户本轮只同意"玩家侧做成本对称"。
  （它每 60 秒才 1 格，量小；AI 是每 10 秒 1 格，才是蔓延主源。）

**实测**：

| 指标 | 基线（原码） | 主干式 | 说明 |
|---|---|---|---|
| 道路总数 | **202** | **133~142** | ✅ **-30~34%** |
| 铺路（玩家 / AI） | 100 / 100 | **100 / 34~35** | AI 侧 **-65%**，玩家侧不变 |
| 终局主城 P50 | 3~4 | 3 | 与基线一致 |
| 胜负 | 80~90% | 80~87% | 一致 |
| 对局时长 | 1199~1280s | 1086~1249s | 一致 |

> 主目标达成：**道路总数 -30% 以上，且 AI 侧 -65%**。玩家侧 100 是因为它顶满了额度上限。

### 26.2 第二步：经济约束（递增单价）—— 实测无效，默认关闭

**设计**：`CFG.map.roadPriceStep` —— 铺一格的单价 = 土路基础价 + `floor(已铺路数 ÷ roadPriceStep)`。
AI 与玩家**共用**（`Game.roadUnitPrice()`；玩家道路卡价 = 基础价 + 政策修正 + **格数 × 当前档位**）。

**三档实测**：

| 档位 | 道路总数 | 玩家 / AI | 训练士兵 | 粮食结余 | 胜负 |
|---|---|---|---|---|---|
| 每 20 格 +1 | 135 | 100 / 35 | 64 | 2391 | 90% |
| 每 10 格 +1 | 142 | 100 / 40 | 73 | 2564 | 93% |
| 每 5 格 +1 | 145 | 100 / 43 | 72 | 1545 | **73%** |
| **关闭（默认）** | **133** | 100 / 34 | 79 | 1852 | 87% |

**铺路格数三档完全一样 → 递增压不住铺路。** 它唯一的效果是把总花费从 200⚡ 抬到 480~650⚡，
挤占建造/训练（每 5 格档胜率掉到 73%、时长顶到 1800s 兜底）——**与「省能量」目标正好相反。**
→ **默认关闭（`roadPriceStep: 0`），机制与公式都保留**，要启用设回 >0 即可。

### 27.4 ⚠️ 本轮三大坑（都值得记住）

1. **Python `http.server` 在 Windows 会从注册表读 MIME** —— 本机 `.css → application/x-css`，而 **Edge 拒绝非 `text/css` 的样式表** → 整页无样式（白底黑字裸文本）。**项目里早就有 `test/server.js`（node，8124，MIME 正确）**，注释还写着"绕开 Windows 注册表污染"—— **本地调试/截图一律走 8124，不要用 python http.server**（本项目第四次"功能写完了没用上"）。
2. **resize 读 `host.clientHeight` 会形成循环依赖**：`#app` 高度是 `100dvh`，而 `#stage/#ui` 的高度又由 resize 设置 —— 实测直接把布局挤崩。**尺寸来源必须是 `innerWidth/innerHeight`（视口）**。
3. **CSS 特异性与 min-height**：`#hand-slots .card`（带 id）会盖过媒体查询里的裸 `.card`，且那条规则还有 `min-height:156px` —— 媒体查询里要同名同特异性、并把 min-height 一起清掉。

## §36 方案A落地 + 弃牌交互重做 + 顶栏收尾（第六十七次修订 · 本地未发布）

## §37 弃牌改「拖到弃牌堆」+ 修角标被挡（第六十八次修订 · 本地未发布）

> 触发：用户「点击弃牌按钮后进入弃牌模式，仍需要玩家拖拽，但弃牌数无限制，或者你看看有没有更好的方案」。

### 37.0 设计取舍
- 用户要**拖拽**而不是点卡 —— 有道理：不限张数的模式下，点一下就弃、一下点错就白丢一张；
  拖拽给一次反悔机会（拖错地方松手 = 取消）。**保留用户的方案，未换别的。**
- 落点用**右下角的弃牌角标本身**（StS 的牌堆指示器），而不是再造一个浮层 —— 浮层上一轮已证明不主流。
- 模式**不自动退出**：进入后可以连弃任意多张，Esc / 再点弃牌角标退出。

### 37.1 实现
- `hitTest()`：`el.closest('#btn-discard')` → `{zone:'discard'}`，**放在卡种过滤之前**
  （此前效果牌/道路牌根本进不了落点判定）。
- `endDrag()`：**仅在弃牌模式下**，任意卡种拖到弃牌堆 = 弃掉；不退出模式。
  非弃牌模式时落在这里 = 普通取消（防误丢）。
- 弃牌模式下点卡**不再直接弃**（照常进入拖拽）。
- `moveDrag()` 拖到角标上时角标放大 + 金圈（`#btn-discard.dz-hover`），提示"松手就弃"。
- `onHandCardClick()` 已无人调用，删除（上一轮为点卡路径抽的方法）。

### 37.2 ⚠️ 连带修掉的更严重旧 bug：右下角标一直点不动
- `.row-body`（手牌行容器）**全宽 + `pointer-events:auto`**，把右下角四个功能角标全部盖住
  —— `elementFromPoint(角标中心)` 返回的是 `row-body`，**角标点不动、弃牌也拖不进去**。
- 修复：`row-body { pointer-events:none }` + `.row-body .card { pointer-events:auto }`
  （容器不拦截、卡牌自身恢复，与 `#hand-bar` 容器的既有做法一致）。
- 修复后实测：点弃牌角标 → 进/出模式正常；拖手牌到角标 → 弃牌成功、模式保持、计数徽章 +1。
- 这解释了此前"弃牌拖不进去"的现象 —— 不只是交互设计问题，是角标根本收不到事件。

### 37.3 验证
五层全绿 · handplace 11/11 · 引用 0 缺失 · 桌面/手机截图零报错。
`uitest.js` 第 9 节改为：五种卡拖弃牌堆全弃 / 模式保持开启 / 计数徽章同步 / 非弃牌模式拖到堆上不弃。

## §38 测试为什么没拦住（复盘）+ fulltest 复活（第六十九次修订 · 本地未发布）

1. **有一整层测试早就死了，而且不在门禁里**。
   `fulltest.js`（37 项真浏览器 UI 全流程：政策/抽卡/建造/升级/行军/任务/结算/相机/暂停）在 §28 加新手引导后

2. **五层测试的天性决定它看不见"长得对不对"**。
   312 条逻辑断言测的是规则；`uitest.js` 用的是 **mock DOM**（`getElementById` 返回假元素），永远看不见
   "元素 A 盖住元素 B"；smoke 只断言"元素存在"。而近期挖出的 bug 大半在表现层：
   遮挡（row-body 盖住四个角标）、尺寸（顶栏被撑到 275px）、素材（不透明底/水印/白边）、堆叠（pane.hidden 失效）、

3. **偶发失败被当成抖动**。
   AI 能量死局的断言其实一直在跑，但它 60~70% 概率会过 —— 重跑就绿，于是被当成"不稳定测试"放过。

  模态弹窗与主菜单盖住背后的 UI 属设计如此，已排除。

### 38.2 ⚠️ 又挖出一个真功能缺失（等策划拍板）：「查看/化解事件」不可达

## §40 资源点视觉重塑（方案A+D，第七十一次修订 · 本地未发布）

## §41 据点素材与地图同源 + 信息牌重做（第七十二次修订 · 本地未发布）

> 触发：用户「和原地图真的适配吗？感觉还是有点小突兀，而且建筑下方的信息界面太丑太朴素了，还是去参考别的游戏怎么设计的」

### 41.0 诊断与查证
- **突兀的根因**：第一版据点素材的 i2i 锚是 **style-ref-2.jpg（UI 风格板）**，而地图是另一幅画
  （plate-vivid，灰绿低饱和的手绘 SLG 棋盘）—— 两幅画的调色板/笔触不同源，贴上去就"跳"。
- **信息牌**：率土/三战的地图牌是「深色薄片 + 归属色 + 资源图标 + 等级数字」，强调"简洁直观、扁平轻薄"；
  率土自己的视觉语言是玄黑/绛红/蚕白。我们的 UI 语言是木纹+羊皮纸+金线 —— 所以信息牌应该用**木纹横幅**，
  与顶栏/按钮同源，而不是一块纯黑矩形。
- 修复思路：**i2i 锚直接换成实机地图裁片**（plate-vivid 草地/河流/山），让模型用地图自己的调色板和笔触作画。

### 41.1 据点素材重做
- 从 `plate-vivid.png` 裁 768×768 作 `_map-anchor.png` → 三张据点素材重新生成（粮仓/石龛水晶/哨塔驿站），
  新版明显更"长在地图上"（灰绿低饱和、同款笔触）。
- `_make_camp.js` 源切换为 `_src2-*`，重新加工（紧裁/键出/腐蚀/192 高）。

### 41.2 信息牌重做（木质横幅）
- 新增 `Sandbox.drawBannerPlate()`：**两端缎带切口的木牌** —— `createPattern(topbar-wood-tile)` 平铺木纹
  （与顶栏同一张贴图，天然同源）+ 轻压暗层 + 深色外框 + **归属色内线**（我方金/敌方红/中立米白）+ 切口尖金铆钉。
- `drawMapLabels` 重写：
  - 资源点：两行牌（`★/✖ 名称` + `产出 · 守军`），归属由内线与文字色表达；
  - **建筑/主城也补上名牌**（此前贴图路径只有 Lv 角标没有名称）—— 率土式"每个对象都标名称+等级"。
- ⚠️ 踩坑：`drawMapLabels` 的 forEach 回调里 `this` 是 undefined（strict vm），`this.drawBannerPlate` 报错
  → 开头 `const self = this` 转交。

### 41.3 门禁稳定性（按"偶发失败必须查根因"的纪律处理）
- 遮挡审计在门禁里偶发失败、单跑却干净 —— 根因：审计死等固定 1500ms，门禁里紧跟着 fulltest 跑、机器负载高时页面未就绪。
  修复：① 等**真就绪条件**（引擎+画布尺寸+字体就位）替代固定时长；② 整轮复检一次，偶发误报不复现即通过。
